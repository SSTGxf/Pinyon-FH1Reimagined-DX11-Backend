Its build cannot target D3D11 — GPU backend selection lives in the SDK (shiftglue-sdk), which is an **empty submodule** in this download, and the consumer repo only selects the `fh1` GPU plugin.

**What IS usable for the D3D11 work is diagnostic/reference material, not backend code.** Ranked:

1. **`tools/check-fh1-texture-watch.py` — CONFIRMED usable.** A lost-write regression test for the texture load lifecycle. It takes `--source` and Seth's rexglue `cache.cpp` has every method it needs (verified by line). This directly tests audit cause #1 (upload rejection). Cheapest next step: run it against Seth's cache.cpp.
2. **`tools/compare-native-renderer-images.py` — usable as-is.** Pure-Python PPM/PNG comparison with MAE/RMSE/coverage-IoU and pass/fail thresholds. Quantifies the black-half and the blue tint instead of eyeballing photos. Cheapest next step: run it on a D3D11 presented PPM vs a reference frame.
3. **`src/ui/hostui/xds_texture.cpp` + `docs/UI_ASSETS.md` — reference for the swizzle fix.** A complete, correct implementation of fetch-constant parsing, tiling, endianness, and swizzle application, with the exact swizzle encoding. Not a drop-in fix (it's a host UI decoder, not the GPU fetch path), but it is the spec for Rank 3.
4. **`config/render-tests/*.fh1test` (50 scripts) — reusable test definitions.** `fh1-opening-sync` and `fh1-fmv` cover the missing intro/cinematic; `fh1-free-roam` covers free-roam; `fh1-smoke` is a minimal smoke test. **What 0.3.0 does NOT contain:** any fix for the texture upload / lost-write problem (the only "lost-write" hit in the whole tree is the texture-watch tool's own docstring), any D3D11 backend, any D3D11 presenter, any swizzle fix for the GPU fetch path, and the shiftglue-sdk GPU backend core itself (empty submodule).

## 2. `src/native_renderer/` — guest_output_renderer and graphics_hooks

### guest_output_renderer.cpp (33 lines) / .h

The whole file is a thin install/uninstall wrapper:

```cpp
bool ObserveRenderTestOutput(const rex::system::NativeGuestOutputRenderContext& context) {
  if (context.phase == rex::system::NativeGuestOutputPhase::kPresented) {
    pinyon_shift::fh1_render_test::ObserveOutput(context);
  }
  return false;  // never claims or modifies the output
}
void InstallGuestOutputRenderer(rex::system::IGraphicsSystem* graphics_system) {
  if (graphics_system) graphics_system->SetNativeGuestOutputRenderer(&ObserveRenderTestOutput);
}
```

What it does: installs a callback on the SDK's `IGraphicsSystem` that fires at the final guest-output boundary; on the `kPresented` phase it hands the context to the render-test observer. Backend-agnostic at the interface level (it goes through the abstract `IGraphicsSystem`, not a specific backend).

**Usable for D3D11? Concept yes, code no.** This is exactly the hook point you would want for the black-half investigation — a present-boundary observer where you can inspect the presented frame and compare it against the guest output. But it depends on two SDK interfaces, `rex::system::IGraphicsSystem::SetNativeGuestOutputRenderer` and `rex::system::NativeGuestOutputRenderContext`, and **neither exists in Seth's rexglue**: a search of `E:\PinyonShift\work\.local\rexglue\include\rex\system\interfaces\graphics.h` for `NativeGuestOutput|SetNativeGuestOutput|ShaderTranslationObserver` returned zero hits. Seth's rexglue is an older SDK version that predates this observer API. The file cannot be dropped into his tree. The portable takeaway is the pattern: observe at the present boundary, return false, never modify the output.

### graphics_hooks.cpp (147 lines) / .h

Guest-code observers, called from the mid-asm hooks in `config/rexglue/analysis`. Three pieces:

- `PinyonShiftObserveGraphicsFrame()` — "FH1's sole VdSwap call is the source-frame boundary used by the real-frame presentation and performance gates. It intentionally changes no guest state." Feeds the critical-path trace and the source-frame counter (`PROFILE_SOURCE_FRAME()`).
- `PinyonShiftObserveTitleDrawEmitterBegin/End` + `PinyonShiftObserveTitleDrawPacketPublish` — title draw-emitter timing samples for the critical-path trace.
- `PinyonShiftGpuFenceWait(PPCRegister& r3)` — the interesting one. Predicate at `0x829F04A8` is what FH1's D3D fence waits call while the GPU fence word has not reached their target. The device keeps a pointer to the fence word at +11024 (written by the command processor's `EVENT_WRITE_SHD`) and a lost-device flag at bit 1 of +11069. Instead of spinning, it spins briefly (20 µs), then blocks on `rex::system::WaitForGpuWrite(GpuWriteSequence(), 1ms)` until the command processor writes guest memory. Gated by cvar `pinyon_shift_block_on_gpu_fence` (default true, hot-reload).

Also defines `pinyon_shift_fh1_gpu_corpus` (bool, default false, requires restart): "Sample native GPU pass and texture-request timings every 60 frames (read by the D3D12 command processor)" — D3D12-specific.

**Usable for D3D11? No, as code.** This is guest-side (mid-asm hooks into FH1's own code), not backend-side. It does not fix `WaitForGpu()` in the D3D11 backend (the open error-handling issue) — that is a host-side D3D11 function; this hook changes how the *guest* waits on its fence. The fence-wait pattern (block on a GPU-write signal with a 1 ms bound instead of spinning) is conceptually related to GPU synchronisation, but it depends on SDK APIs (`GpuWriteSequence`, `WaitForGpuWrite`, `kernel_state()->memory()`) and guest addresses specific to FH1's D3D fence waits. Reference only.

### shader_capture.cpp (430 lines) / .h (also in native_renderer)

Captures shader translations via `IGraphicsSystem::SetShaderTranslationObserver`. For each translated shader it validates the bytecode magic (DXBC for D3D12, SPIR-V for Vulkan), records guest hash, specialization mask, texture bindings (`bindless_descriptor_index`, `fetch_constant`, `dimension`, `is_signed`), sampler bindings, and `used_texture_mask`, then writes `dxil.blob` + `shader-manifest.json` (schema `pinyon-shift.native-shader-pack.v3`).

Backend enum is explicit and closed:

```cpp
// Fh1ShaderPack::Backend values.
constexpr uint32_t kBackendD3D12 = 1;
constexpr uint32_t kBackendVulkan = 2;
```

**No D3D11 backend value exists.** The manifest `"backend"` is `"d3d12"` or `"vulkan"`. D3D11 shaders are DXBC, so the magic check would pass, but the manifest would mislabel them `d3d12`, and the whole thing depends on the `SetShaderTranslationObserver` SDK interface that Seth's rexglue does not have (verified above). **Not usable for D3D11 as-is.** The capture format (guest hash + bindings + used_texture_mask) is a useful reference if Seth ever wants a shader pack for D3D11, but that is not an open issue.

## 3. `src/fh1_render_test.cpp` / .h (1,171 lines) — the scripted render test

A deterministic, scripted render-test harness. It loads a `.fh1test` script (schema `pinyon-shift-fh1-render-test-v1`, env vars `PINYON_SHIFT_FH1_RENDER_TEST_SCRIPT` / `PINYON_SHIFT_FH1_RENDER_TEST_OUTPUT`), replaces physical input with a synthetic controller stream, and observes the real presented output.

Script commands (parsed in `LoadScript`):
- `input <frame> <buttons-hex> <lt> <rt> <thumb_lx> <thumb_ly> <thumb_rx> <thumb_ry>` — deterministic gamepad steps.
- `wait <frame> <max-frames> <vehicle|vehicle-moved <dist>|movie <text>|file <text>>` — holds the script clock (inputs hold state) until the game reaches the condition.
- `hostkey <frame> <f6|f7|f8|f10|enter|escape|up|down|left|right|space>`, `hostclick <frame> <left|right> <x> <y>` (1280×720 title space), `xamdialog <frame> <message|keyboard|achievements|toast>` — drive host-drawn screens the controller cannot reach.
- `cvar <frame> <name> <value>` — set a cvar mid-run.
- `mark` / `scanpoke` — copy the title's committed virtual heap pages (0x00010000–0x40000000, 0x40000000–0x7F000000), find floats that rose by a consistent step between ≥3 marks, poke a slice of candidates. A memory-value finder.
- `snapshot <frame> <name>` — write 512 MB (0x20000000) of guest physical memory to `<name>.mem` for offline scans (`tools/scan-guest-snapshots.py`).
- `poke <frame> <address-hex> <float>` — store a big-endian float at a guest physical address.
- `capture <frame> <name>`, `stop <frame>`, `# clock-hz <n>` (wall-time pacing, ≤240 Hz).

`ObserveOutput` runs at each presented output frame (`NativeGuestOutputRenderContext`): applies waits, dispatches host steps, triggers captures (a missed capture frame is a failure), and stops cleanly at `stop_frame`. Captures go through `presenter->CaptureGuestOutput(image)` and are written as P6 PPM by `WritePpm` (RGBA → first 3 bytes per pixel), with a diagnostics event carrying name, frame, trigger output frame, elapsed times, dimensions, presenter (`"native"`), vehicle pose, and an FNV-1a hash of the raw image. `ObserveMovieOpened` / `ObserveFileOpened` / `ObserveVehiclePose` feed the wait conditions.

**Usable for D3D11? The framework no, the test scripts yes.**
- The framework depends on SDK interfaces Seth's rexglue does not have (`IGraphicsSystem`, `NativeGuestOutputRenderContext`, `Presenter::CaptureGuestOutput`, `InputSystem`/`InputDriver`, `WindowedAppContext`). It cannot be dropped into his tree. Porting it would mean backporting those SDK interfaces — a large job, not a quick win.
- The **`.fh1test` scripts themselves are plain text and backend-agnostic** — they describe inputs, waits, and captures, not a backend. 50 of them live in `config/render-tests/`. The most relevant to Seth's open issues:
  - `fh1-opening-sync.fh1test` — the new-player opening: waits for movie `pressstart`, captures `press-start`, `single-player`, waits for file `trackroute170`, then the opening drive in the Viper, captures `opening-drive` / `opening-drive-later`. This is the exact intro/cinematic sequence that is black/missing in Seth's build.
  - `fh1-fmv.fh1test` — "Run with --include-opening-movies to cover FH1 startup/FMV composition." Captures `opening-60/180/300` at 60 Hz clock. Directly covers the missing intro.
  - `fh1-free-roam.fh1test` — free-roam with A presses every 120 frames, captures `probe-1200/1500/1800`, plus `# expect-image probe-1200 12 30 1.00` annotations (image thresholds) and `# expect-performance` / `# expect-simulation-time` lines.
  - `fh1-smoke.fh1test` — idle smoke test: deterministic input, exact-frame readback, clean self-termination. Capture `boot` at 300, stop 330.
- `tools/run-fh1-render-test.py` (40 KB) is the runner: prepares isolated state (copies `user/config/mods/user-modded` from a seed), seeds FH1 shader storage (`fh1-native-shaders-v2.bin`, `fh1-native-pipelines-v1.bin`), seeds **Vulkan** shader storage (`.xsh`, `.fbo.vk.xpso`), seeds the FH1 pipeline prewarm allowlist (`fh1-gpu-prewarm-v3.txt`), parses `FH1 V5 pass family` performance log lines, compares vehicle poses against baselines, and checks `# expect-*` annotations (default image limits `(12.0, 30.0, 0.60)`). It is tied to the 0.3.0 binary and its state layout and Vulkan shader seeding — **not directly runnable against Seth's D3D11 build**. Its image-threshold defaults and the `expect-image` annotation format are reusable as a spec.

## 4. Tools — per-script verdicts

### check-fh1-texture-watch.py — USABLE, highest value

What it does: extracts the production texture-load lifecycle methods from a `cache.cpp` — `PrepareTextureLoad`, `CommitPreparedTextureLoad`, `LoadTextureData`, `WatchCallback` (both `Texture::` and cache-level), plus either `MakeUpToDateAndWatch` or `WatchPendingLoad` + `CompleteLoad` — embeds them in a mock-`SharedMemory` harness (watches, GPU/CPU writes, failures), compiles with `clang++ -std=c++20`, and runs a battery of checks:
- baseline load becomes clean and preserves exactly two watches;
- CPU success skips residency; writes survive completion; failed attempts fall back;
- partial CPU imports preserve a write to the unrequested sibling;
- each writer/source stage must leave its region dirty after loading (GPU or CPU write during load → `outdated_mask` set for that part, `texture_became_outdated` set, reload clears it);
- a base write must survive a mips-only load;
- failures (memory / backend / scaled-resolve) → `LoadTextureData` false, `outdated_mask == 3`, retry succeeds;
- a failed batch can prepare again without leaking or replacing valid watches.

Default source is `thirdparty/shiftglue-sdk/src/graphics/pipeline/texture/cache.cpp` (absent — empty submodule), **but it takes `--source`**, so it can be pointed at any `cache.cpp`.

**Verified against Seth's tree:** his rexglue `src/graphics/pipeline/texture/cache.cpp` contains every method the harness needs:
- `TextureCache::PrepareTextureLoad` — line 491
- `TryLoadTextureDataFromCpu` — referenced line 538 (the harness keeps the CPU-success test block only if this exists; it does)
- `TextureCache::CommitPreparedTextureLoad` — line 570
- `TextureCache::Texture::WatchPendingLoad` — line 995
- `TextureCache::Texture::CompleteLoad` — line 1010
- `TextureCache::Texture::WatchCallback` — line 1065
- `TextureCache::WatchCallback` — line 1086
- `TextureCache::LoadTextureData` — line 1233

This is the `WatchPendingLoad`/`CompleteLoad` variant (no `MakeUpToDateAndWatch`), which the harness explicitly supports. **This directly tests texture-audit cause #1 (upload rejection / lost write)** against Seth's own shared cache code — the same cache the D3D11 backend's `texture_cache.cpp` sits on top of. Note it tests the *shared* cache lifecycle, not the D3D11-specific `GetActiveTextureBindfulSRV` bind path (audit cause #2) — a pass here would point at cause #2, a fail would confirm cause #1.

## 5. Config / cmake — can 0.3.0's build target D3D11?

**No.** 
- `cmake/PinyonShiftRexGlue.cmake` pins ReXGlue SDK **0.10.0** (`find_package(rexglue 0.10.0 EXACT ...)`, or `REXSDK_DIR` for a source tree) and attaches the GPU backend with `rexglue_configure_target(${target_name} GPU_PLUGINS fh1)` — the `fh1` GPU plugin (`rexgpu-fh1.dll`). There is no backend option in the consumer build; backend selection lives inside the SDK.
- `config/rexglue/pinyon_shift_manifest.toml` pins `sdk_version = "0.10.0"` and contains no backend selection.
- `config/` also holds `config/render-tests/` (50 `.fh1test` scripts, see §3), `config/rexglue/analysis/` (main-xex, speech/xmedia facade TOMLs), and `config/mod/fh1-symbols.toml`.
- The launcher (`launcher/PinyonShift.Launcher/`, a WPF C# app: `App.xaml.cs`, `MainWindow.xaml.cs`, `PortableMode.cs`, `RouteStep.cs`) builds/launches the preview; it has no D3D11 option (its backend references are the `gpu_backend`/`renderer` settings in `pinyon_shift_app.cpp`, §1).

To get a D3D11 build out of 0.3.0 you would need the shiftglue-sdk source (empty submodule) *and* a D3D11 backend inside it, which upstream does not have. 0.3.0 cannot be used as a D3D11 test vehicle.

## 6. Anything else directly useful

- **Swizzle reference — `src/ui/hostui/xds_texture.cpp` + `docs/UI_ASSETS.md`.** `DecodeXds` is a complete, self-contained XDS texture decoder and the exact spec for the fetch swizzle. It parses the 6-dword big-endian fetch constant and extracts: format (`fetch[1] & 0x3F`), width/height (`fetch[2]`), pitch, tiled flag, endian mask (`kEndianMasks[(fetch[1] >> 6) & 3]`), **swizzle `(fetch[3] >> 1) & 0xFFF`**, packed-mips flag. It untiles with a local `TiledOffset2D` (full Xenos tiling formula, lines ~150–160), undoes endianness (`block[i] = payload[offset + (i ^ mask)]`), decodes BC1/BC2/BC3/BC4/32-bit blocks, and applies the swizzle per texel: `selector = (swizzle >> (3*channel)) & 7; out[channel] = selector < 4 ? texels[i][selector] : (selector == 5 ? 255 : 0)`. `UI_ASSETS.md` documents the formats: RGBA8 uses `ZYXW` swizzle (2,671 textures), `k_DXT3A` uses a `111W` swizzle, one-channel formats read the same value in every component ("the SDK's RRRR host swizzle"). **This is a reference for the Rank 3 fix, not a drop-in fix:** it is a host-side UI-asset decoder, a different code path from the GPU texture fetch. The D3D11 backend needs the equivalent (`GuestToHostSwizzle`) in its fetch/bind path, as D3D12/Vulkan do. Use this file and the doc as the encoding spec when implementing it. Also note `tools/inspect-fh1-ui.py` (and its tests) exercises this decoder, and `tools/extract-fh1-shader-corpus.py` has swizzle-related handling — both are UI/shader-corpus tools, not backend fixes.
