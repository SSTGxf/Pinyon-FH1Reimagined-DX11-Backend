## Rank 1 — All three bands draw into surface rows 0–256, overwriting each other (the untile system is entirely absent on D3D11)

**(a) Evidence (confirmed in code).** The shared draw setup applies the window offset, but D3D11 never compensates for it anywhere:
- `src/graphics/util/draw.cpp:387-391` — `GetViewportInfo` adds the window offset to `ndc_offset` when `vtx_window_offset_enable`.
- `src/graphics/util/draw.cpp:607-612` — `GetScissor` adds it to the scissor unless `window_offset_disable`.
- `src/graphics/d3d11/command_processor.cpp:1138-1142` — D3D11 applies the viewport from `viewport_info`; `:1186-1194` applies the scissor via `RSSetScissorRects`, with no compensation.
- `command_processor.cpp:1835-1840` — tile claims use the same EDRAM-space rect (`claim_y0 = max(viewport_y, scissor_y)`).

So band 1 lands at rows 0–256, band 2 (offset −256) also at 0–256, band 3 (offset −512) at 0–208 — each overwriting the last. Surface rows 256–512 are never written by any band. The resolve then reads rows 0–720: rows 0–208 hold the last band's content at the wrong dest rows, rows 208–720 hold zeros/stale content. `Fh1ResolveRectangle` (`src/graphics/fh1_edram_resolve.cpp:28-38`) likewise adds `PA_SC_WINDOW_OFFSET` when `vtx_window_offset_enable`, so the plan rect is in EDRAM space, and D3D11 never converts destination Y into a source row — the resolve rect *is* the source row range (`IssueCopy`, command_processor.cpp:3701; `PlanResolveMemory`, fh1_native_resolve.cpp:261; shader `fh1_native_resolve_memory.cs.hlsl:212`, `pixel = rect_origin + thread.xy`).

The whole untile system is missing on D3D11 — absence confirmed in code, in all four parts (Vulkan `src/graphics/vulkan/fh1_native_executor.cpp`): (i) no viewport shift down to screen rows (D3D12/Vulkan shift `viewport.y += untile_rows`); (ii) surfaces sized to plain 512-row `Fh1D3D11SurfaceHeight`, not `full_rows = max(height, untile_height_)` (Vulkan :778–781, :912); (iii) no `EndUntiledTiling` copy-down (Vulkan :744–763) — zero hits in D3D11; (iv) no `(untile_band << 16)` row offset at resolve time (Vulkan :3107, :3147; `untile_band = max(0, -window_y_offset)`, :2936–2937). The shader defines the offset (`fh1_native_resolve_memory.cs.hlsl:236-238`, `fh1_source_row_offset = FH1_SAMPLE_SELECT >> 16u`), but D3D11 passes it as zero: `copy_sample_select` is a 3-bit field (`include/rex/graphics/util/draw.h:405`), `PlanResolveMemory` (fh1_native_resolve.cpp:268) does `plan.constants[4] = sample_select` verbatim, and the trace writer hardcodes `source_row_offset=0` (command_processor.cpp:4018). Zero occurrences of `untile` as code in D3D11's executor/resolve files; `PA_SC_WINDOW_OFFSET` appears in D3D11 only in three log lines (command_processor.cpp:1130, 1845, 4010) — never applied to a viewport, scissor, clear, or resolve. Note the subtlety: the missing row offset *alone* is self-consistent on D3D11 (draws and resolves both use EDRAM rows) — the breakage is that nothing ever moves content to screen rows, and the dest side has no band compensation either. Whether the guest advances `RB_COPY_DEST_BASE` per band is guest behavior, not determinable from code.

**(b) Symptoms explained:** mostly-black free-roam frame with a flickering bright quad / occasional fragments of sky/terrain (one band's content, misplaced at the top, the rest black); which fragment shows varies with pass order and stale surface contents. Also consistent with the static view once showing the world (if the last-drawn band happened to be band 1, rows 0–256 are correctly placed and look like a real scene) plus the black-rectangle artifact (the never-written rows).

**(c) Status:** confirmed in code. Its exact contribution as the *systemic* cause is inference only in the sense that the dest-side guest behavior (dest_base advance per band) is unknown.

**(d) Runtime evidence:** `fh1_swap_fetch_trace=1` → `"FH1 resolve source bands: … nz=[…]"` per-60-row profile and `"FH1 resolve key: … rect=… sample_select=… src=…"` (command_processor.cpp:3757–3762, 3821–3832). Content only in rows 0–256 at resolve time confirms it; nonzero rows 256–512 would rule it out. The `resolve key` lines also show whether `plan.dest_base` is the same or advancing per band (same = dest overwrite; advancing = dest side fine).

## Rank 3 — D3D11 drops the guest fetch's red/blue swizzle (the blue cast)

**(a) Evidence (confirmed in code).** The presented frame goes `IssueSwap` → `RequestSwapTexture` (fetch constant 0) → `PresentGuestOutputTexture` → bilinear blit → `R10G10B10A2` mailbox → paint to `B8G8R8A8` swap chain.
- D3D12 applies the fetch swizzle in the swap SRV itself, `src/graphics/d3d12/texture_cache.cpp:1472-1474` (`srv_desc_out.Shader4ComponentMapping = GuestToHostSwizzle(fetch.swizzle, GetHostFormatSwizzle(key)) | …`), and per draw binding (:887–889, :898–900).
- Vulkan computes it from the same fetch, `src/graphics/vulkan/texture_cache.cpp:1513-1522` (derives `swap_source_needs_rb_swap` when the swizzle is BGR), and selects RB-swap gamma pipelines at present (`src/graphics/vulkan/command_processor.cpp:4765-4781`).
- D3D11 does neither. `src/graphics/d3d11/texture_cache.cpp:769-856` (`RequestSwapTexture`) just returns the texture's stock SRV (`:854-855`, `texture->srv()->AddRef(); return texture->srv();`). `CreateHostSRV` (`texture_cache.cpp:317-353`) sets only `Format`/`ViewDimension` — a D3D11.0 SRV desc has no component-mapping field. Repo-wide grep for `GuestToHostSwizzle` under `src/graphics/d3d11/` returns **zero hits**; grep for `fetch.swizzle`/`fetch_swizzle`/`key.swizzle` in `d3d11/texture_cache.cpp` returns **zero hits**. The shared shader translator also contains zero swizzle handling. The present blit is channel-verbatim, `src/ui/shaders/d3d11/guest_output.hlsl:296-301` (`float3 color = xe_bilinear_source.SampleLevel(…).xyz; return float4(color, 1.0);`) — no swap flag, no constant for one. The only R/B correction anywhere in the D3D11 present path is the diagnostic `pinyon_present_swap_rb` (`src/ui/d3d11/d3d11_presenter.cpp:37-39`, default `false`), and it fires only in the cross-adapter CPU upload leg (`:567`, `if (ten_bit && REXCVAR_GET(pinyon_present_swap_rb))`), inside `CopyGuestOutputToPresent`, which returns `false` immediately when the present device is not separate (`:487-489`). On the normal single-adapter path there is no swap correction at all. The D3D12 presenter has no `pinyon_present_swap_rb` at all — because it doesn't need one. Formats are identical across backends (`include/rex/ui/d3d11/d3d11_presenter.h:44,47`: `kGuestOutputFormat = R10G10B10A2_UNORM`, `kSwapChainFormat = B8G8R8A8_UNORM`).

**(b) Symptoms explained:** the blue cast, exactly — including the Viper: yellow is R+G; with R↔B dropped it becomes B+G, i.e. cyan/blue. It also fits "HUD colors look correct" / "menus render fine": ordinary textures and direct 2D draws use the format-default fetch swizzle, so dropping the per-fetch override is invisible for them; it only shows where the guest sets a non-default (BGR) fetch swizzle — the swap/framebuffer fetches. This is a *different* swap from the resolve's dest_info bit 6 (see Ruled out below). It explains the blue cast only — not the black free-roam screen.

**(c) Status:** confirmed in code that D3D11 lacks the handling both other backends have. **Inference** that FH1's frontbuffer/frame fetch swizzle is in fact BGR — that value was not read from a live run.

**(d) Runtime evidence:** set `fh1_swap_fetch_trace=true` and read the `FH1 swap trace:` line (command_processor.cpp:5232–5244) — it logs `fetch0=[dword_0..3]` plus `fmt=`; decode `fetch.swizzle` from it, in-game vs in a menu. BGR in-game + default in menus confirms the mechanism and the symptom split. Also the presenter's probe (`d3d11_presenter.cpp:808-838`, every 300th frame): `D3D11Presenter: blit bands frame={} sky={r}/{g}/{b} road={r}/{g}/{b}` — if the sky band shows r > b, the swap texture is delivering R/B-swapped channels. Discriminator for *where* the swap is lost: `fh1_debug_composite_dump_world` / `fh1_debug_composite_dump` (command_processor.cpp:1965–2046) — if the world is already swapped there, the loss is at the composite's texture sample; if correct there but swapped in the blit probe, the loss is at present. Note: setting `pinyon_present_swap_rb=true` is **not** a valid test of this on the single-adapter path — it only affects the cross-adapter leg, so no change there would itself confirm the gap.

## Rank 5 — A full-frame 720-row resolve reads rows 512–719 past the 512-row 4x source

**(a) Evidence (arithmetic confirmed, occurrence unconfirmed).** For a 1280-wide 4x surface: `Fh1PitchTiles` gives pitch 32 (`(1280<<1 + 79)/80`); `Fh1SurfaceHeight` (`include/rex/graphics/fh1_edram_surfaces.h:76-84`, constants `xenos.h:411-413`: tile 80×16 samples, 2048 tiles) gives `tile_rows = ceil(2048/32) = 64`, height `= 64 × (16>>1) = 512` rows. So the 4x scene texture is **1280×512** (at 1x it would be 1280×2048 — the full frame fits). A resolve rect spanning rows 512–720 against it reads out of bounds: in the shader's same-place path (`fh1_native_edram.hlsli:333`) that's a direct texture read at rows 512–719 of a 512-row texture (D3D11 returns 0 for OOB SRV loads → black); in the relocated path (`:375`) the EDRAM tile math wraps with `& 2047u`, reading wrong (wrapped) tiles instead of black. Whether that overflow actually occurs depends on the resolve rect: a per-band resolve (rect rows 0–256) fits; a single 1280×720 rect does not. The only runtime resolve line on disk is a 1280×720 resolve — but with `samples=1` (a 1x surface, 2048 rows, so it fits). **No current-build line yet shows a 720-row rect against a 4x source.**

**(b) Symptoms explained:** bottom ~29% of the frame (rows 512–720) black in a full-frame resolve; or doubled/repeated terrain if the resolve takes the relocated path (consistent with the earlier "mountains doubling" complaint, but that link is inference). Distinct from Rank 1 (which kills rows 256+ by never writing them); both can coexist.

**(c) Status:** arithmetic confirmed; occurrence unconfirmed.

**(d) Runtime evidence:** run with `pinyon_resolve_trace=true` in free-roam and read `resolve-trace.log`: the `RESOLVE … rect=…,{}-{},{} … resolve_key=… source_key=… source_size={}x{} samples={} window_y={}` lines (command_processor.cpp:4017–4026) plus `OWNER … rect=… source_size=…` lines (:4035–4046). ## Rank 6 — Resolve rect collapses via scissor/window-offset (silent skip) — code path confirmed, occurrence unconfirmed

**(a) Evidence.** A resolve fires only from a copy-mode draw (command_processor.cpp:1724–1727: `edram_mode == kCopy → IssueCopy()`). `IssueCopy` (command_processor.cpp:3544–3561) requires `Fh1PlanResolve` to succeed with `plan.copy`. Gate 1: `Fh1ResolveRectangle` must return non-empty (`fh1_edram_resolve.cpp:11-59`) — rect comes from vertex fetch 0 of the copy draw (must be `kVertex`, 3 verts × 2 floats, else `return false` → `plan.empty = true`), plus `PA_SC_WINDOW_OFFSET` if `vtx_window_offset_enable`, then clamped to the scissor (`draw_util::GetScissor`, `src/graphics/util/draw.cpp:600-613`, which adds the window offset to the scissor too unless `window_offset_disable`), 16-px aligned, clamped to surface pitch. **If this returns false, `IssueCopy` returns `plan.empty` (true) silently — no warning, no log line, no resolve** (command_processor.cpp:3558–3561). This is the only fully silent skip path. Other gates log a skip reason: `GetResolveInfo` failure → `plan.skip = "resolve_info"` (fh1_edram_resolve.cpp:79–83); dest format/array/endian/source format → `"resolve_dest_format"` / `"resolve_dest_array"` / `"resolve_dest_endian"` / `"resolve_source_format"` (:129–141), logged as `REXGPU_WARN("D3D11 FH1 native resolve: skipped ({})", …)` after applying resolve clears (command_processor.cpp:3617–3621); zero-length extent → `copy=false`, no skip reason → warn "skipped (unknown)" (:99, :3617–3621). If during driving the guest sets a scissor that doesn't intersect the shifted quad — or `vtx_window_offset_enable` is set while the quad is already in surface space, or vice versa — the rect shrinks to one band, a few rows, or empty.

**(b) Symptoms explained:** a small-but-nonempty rect would resolve exactly one strip/quad of content and leave the rest of the frontbuffer stale — matching "one bright quad, rest black". An empty rect (silent skip) would leave the whole frame stale/black.

**(c) Status:** code path confirmed; occurrence not confirmed.

**(d) Runtime evidence:** `fh1_debug_resolve_trace` (command_processor.cpp:3845–3863, logs one `FH1 resolve trace: swap=… rect=…` line per copy, default 0) or `fh1_debug_tile_trace_swap` (logs `FH1 resolve clear flags: … rect=… copy=… skip=…`, command_processor.cpp:3591–3616). Both are off in the preview config. A missing/skipped `copy=0` or an empty rect on driving frames confirms it.

## Rank 7 — Owner-split reads an empty/wrong surface — code path confirmed, occurrence unconfirmed

**(a) Evidence.** `IssueCopy` splits the rect by owner (command_processor.cpp:3706–3731, `SplitByOwner` in `include/rex/graphics/fh1_edram_tiles.h:150-196`) and dispatches one resolve per owner rect, with `source.surface` taken from the *first* non-resolve-key owner found (command_processor.cpp:3723–3739). If band 1's tiles are owned by a different surface than the resolve key (e.g. the previous frame's composite, or a stale owner after a claim), the dispatch reads that surface. `SplitByOwner` itself preserves Y with no remapping or clamping error (tile height `16 >> msaa`, command_processor.cpp:3712–3716), and the same `dest_base` for every owner region is **not** a bug — dest addressing is absolute in `pixel` (shader `:231-232`, `address = fh1_dest_base + TiledOffset2D(pixel.x, pixel.y, …)`), so each region writes its own correct dest rows.

**(b) Symptoms explained:** band 1 resolving zeros (Rank 2) if its tiles' owner surface is empty/stale.

**(c) Status:** code path confirmed; occurrence not confirmed.

**(d) Runtime evidence:** `fh1_debug_resolve_owner_census=1` (census log `FH1 resolve owner census: …`, fh1_native_executor.cpp:2223–2283) or the `OWNER`/`OWNER_RESULT` lines in `resolve-trace.log` (command_processor.cpp:4027–4040, 4063–4067, 4150–4166) — none exist yet. Note the census trap: it filters to nonzero base tile, pitch 16, colour only, 1x MSAA only, so it cannot establish mixed ownership for the main 4x scene resolve.

## Rank 8 — `window_offset_disable` could make band draws/resolves vanish entirely — code path confirmed, runtime value unknown

**(a) Evidence.** `GetScissor` applies the window offset only `if (!window_offset_disable)` (draw.cpp:607–612). If the game sets `window_offset_disable` on a band draw, the scissor stays in screen rows (e.g. 256–512) while the vertex shift (`ndc_offset`, draw.cpp:387–391) still moves geometry to EDRAM rows (0–256) — the draw is scissored out completely. The same flag feeds `Fh1ResolveRectangle`, whose scissor clamp (fh1_edram_resolve.cpp, clamp to `scissor.offset/extent`, then `return x0 < x1 && y0 < y1`) can collapse a band's resolve rect to empty (`plan.empty` → no resolve). Instrumented by the `"FH1 tile draw: … window_y={} vtx_window_offset_enable={} window_offset_disable={} viewport_y={} … scissor_y={} … claim_y={}..{}"` log (command_processor.cpp:1849–1856, gated by `fh1_debug_tile_trace_swap`).

**(b) Symptoms explained:** if set for bands 2–3, only band 1 ever draws/resolves — a frame that is at best the top band plus black, matching the mostly-black symptom even more extremely than Rank 1.

**(c) Status:** code path confirmed; runtime value unknown.

**(d) Runtime evidence:** set `fh1_debug_tile_trace_swap` to a presented frame and drive; the `"FH1 tile draw:"` lines give `window_offset_disable` and `claim_y` per draw. `window_offset_disable=1` with `claim_y` in screen rows while `window_y` is −256/−512 confirms it; `=0` rules it out.

## Rank 9 — Staging-copy or swap-readback extent mismatch — code path confirmed, occurrence unconfirmed

**(a) Evidence.** After the dispatch, the mirror update can fail: the dispatch writes a small staging buffer; `CopyResolveStagingToHost` lands it in the mirror (command_processor.cpp:4840–4859). On failure `complete = false` and a once-only error is logged: `"D3D11 FH1 native resolve: staging copy to the mirror failed ({:08X}+{})"`. A failed staging copy means the mirror (and therefore the presented frame) keeps stale content. No such error is visible without the stdout log, which is not currently captured to a file. Separately, the presented frame is the swap fetch's extent read back from the mirror (command_processor.cpp:5331–5348), not the resolve's extent — if the fetch names a different base/length than the resolves wrote, the presenter shows stale guest memory (black/boot frame). If the swap texture can't be built at all, `IssueSwap` warns once: `"D3D11 IssueSwap: the frontbuffer is not resolvable as a guest texture … - presenting black"` (command_processor.cpp:5395–5400) — this line never appeared in runtime.log.

**(b) Symptoms explained:** stale/black presented frame despite resolves running.

**(c) Status:** code path confirmed; occurrence not confirmed.

**(d) Runtime evidence:** `fh1_swap_fetch_trace=true` → `FH1 frontbuffer readback: … readback_words_nz=… guest_words_nz=…` (command_processor.cpp:5349–5374); a mismatch between the two counts confirms the readback didn't land.

## Rank 10 — The scissored clear literally draws one triangle — confirmed code, weak fit

**(a) Evidence.** `ResolveClear` sets a full-surface viewport and `RSSetScissorRects(1, &rect)` then `context->Draw(3, 0)` (fh1_native_executor.cpp:2480–2496) — a single fullscreen triangle clipped to the resolve rect. `ResolveClear` (fh1_native_executor.cpp:2321–2347) clamps the clear rect to `geometry.surface_width/height` and silently no-ops (`return true`) if the clamped rect is empty; the source surface is 1280×512, so a 720-row rect clears at most 512 rows. The clear runs **after** the dispatch (command_processor.cpp:5045, `complete &= apply_resolve_clears()`), so a clear cannot blank the just-resolved band — but it does blank the surface for the *next* band's draw if the rect is wrong (e.g. a 720-row rect clamped to the 512-row surface clearing rows the next band still needs).

**(b) Symptoms explained:** at most indirectly — it clears the EDRAM surface, not the screen, so it cannot itself be the bright quad on screen.

**(c) Status:** confirmed code; weak fit as a cause.

## Rank 12 — Smaller confirmed divergences with no pixel effect established

- **No depth-overwrite fast path in D3D11.** D3D12 detects depth-only draws with zfunc Always + z-write and claims only the overwritten rects (`src/graphics/d3d12/fh1_native_executor.cpp:1307-1310`, then `:1341-1344` `ClaimDepthOverwriteTiles`, `:1157-1202`). A grep for `depth_overwrite|DepthOverwrite|overwrite` across `src/graphics/d3d11/` finds no equivalent. D3D11's `PrepareTargets` (d3d11/fh1_native_executor.cpp:674–754) always claims the full draw rect via `ClaimTargetTiles` (:750–751, 756–830), which transfers the previous owner's content in first. **Symptom: none established** — the transferred content is overwritten by the draw itself, so this is a perf divergence, not a pixel-correctness one. Runtime check: `D3D11 FH1 native executor: frame=… claims={} tiles={} transfers={} transfer_tiles={}` (fh1_native_executor.cpp:2531–2546, every 100 frames) — elevated transfers on depth-heavy frames vs D3D12 would corroborate.
- **Per-surface `stencil_nonzero` maintained only by clears in D3D11.** `include/rex/graphics/d3d11/fh1_native_surfaces.h:42` (`bool stencil_nonzero = false`), written only in `ResolveClear` (d3d11/fh1_native_executor.cpp:2501–2502). D3D12 sets the same flag on any depth-stencil-writing draw (`src/graphics/d3d12/fh1_native_executor.cpp:1325`), on top of per-tile tracking (`MarkTileStencil`/`AnyTileStencil`, :590–737). D3D11 does have per-tile `tiles_.MarkStencil` (ClaimTargetTiles :805–807, 825–829; ResolveClear :2459–2464), so tile-level tracking is not missing — only the surface-level flag's update sites differ. **Symptom: none established** — no D3D11 read site found where the stale flag would change pixels.
- **D3D11 failed-swap black-clear vs D3D12 keep-last-frame.** D3D11 clears the mailbox to black and still publishes on a failed swap (command_processor.cpp:5411–5443); D3D12 logs `IssueSwap: RequestSwapTexture failed - fetch0: …` and returns early without refreshing (`src/graphics/d3d12/command_processor.cpp:1936-1943`), keeping the last good frame. **Symptom: black instead of frozen-last-frame on any failed swap; flicker-to-black. Ruled out for these runs** — the `no blit` / `not resolvable` warnings never appear in runtime.log.

## Ruled out explicitly (do not re-chase)

- **Missing cinematic/video presentation path — NOT FOUND; hypothesis unsupported.** Exhaustive whole-tree search for `movie|cinematic|XMediaFacade|Bink|XMV|XVideo|PlayMovie|overlay|video` found zero video/movie player, zero Bink/WMV decoder, zero guest video overlay, zero YUV path, zero second swap chain. The guest's `VdSwap` (`src/kernel/xboxkrnl/xboxkrnl_video.cpp:440`) always writes fetch constant 0 + a `PM4_XE_SWAP` packet — every VdSwap reaches `IssueSwap`, including during video playback. A CPU-decoded video frame would still have to be drawn as a texture and resolved through the single path, so a video-specific failure would sit in draw/resolve handling of the video quad, not in a missing presenter branch. Runtime evidence that would revive it: `fh1_swap_fetch_trace` showing fetch0 as a non-2D/YUV descriptor during the cinematic — but no such rejection was logged, and all intro swaps uploaded successfully.
- **Resolve dest_info bit 6 IS honored, by the shared shader, identically on all backends.** `src/graphics/shaders/fh1_native_resolve_memory.cs.hlsl:256` gates the raw-word fast path on `((FH1_DEST_INFO >> 6u) & 1u) == 0u`, and `:272-274`: `if ((FH1_DEST_INFO >> 6u) & 1u) { color = color.bgra; }`. The D3D11-only cvar `fh1_resolve_swap_rb` (`src/graphics/flags.cpp:103-104`, default `false`; applied at `src/graphics/d3d11/fh1_native_resolve.cpp:248-256`, `dest_info ^= 1u << 6`) is live, not dead — but it is a *resolve-side* inversion, distinct from the fetch-side gap in Rank 3.
- **ResolveClear DOES claim tiles before clearing.** `src/graphics/d3d11/fh1_native_executor.cpp:2446-2468`: per-tile `tiles_.Claim(…, transfer)`, `QueueTransferRun`, `FlushClaimTransfers`, then the scissored clear draw — matching D3D12's claim-then-clear order (d3d12/fh1_native_executor.cpp:1860–1884). - **Recorded-resolve OM unbind IS honored on replay.** `src/graphics/d3d11/command_list_immediate_sink.cpp:136-137` (`if (packet.unbind_om) context_->OMSetRenderTargets(0, nullptr, nullptr);`); both immediate (fh1_native_resolve.cpp:394–399) and replayed (command_list_immediate_sink.cpp:170–176) paths unbind CS SRVs/UAVs after dispatch.
- **Transfer bind order is safe.** `TransferRects` binds the destination RTV first (fh1_native_executor.cpp:1043) and the source SRV after (:1056); same-geometry transfers use an exact `CopySubresourceRegion` (:971–976); depth transfers explicitly unbind the OM first (:1265); a missing previous-owner surface skips cleanly (:937–943).

Shared loop skips predicated packets (`src/graphics/command_processor.cpp:2297-2300`); `PredicatedOut` (:2489–2503) uses `bin_select_`/`bin_mask_` from `PM4_SET_BIN_SELECT[_LO|_HI]` / `PM4_SET_BIN_MASK*` packets (:2449–2465); `TilingPassOfSelect()` (`include/rex/graphics/command_processor.h:518-522`) maps select 3→pass 0, 0xC→pass 1, 0x30→pass 2. List-compiler replay re-checks the predicate (`src/graphics/d3d_list_compiler.cpp:661-671`). - **No camera-dependent path exists in the D3D11 backend.** `fh1_camera.cpp` exists only under `src/graphics/vulkan/`; no D3D11 file references camera state. The static-vs-driving difference has to come through the frame's draw/resolve sequence.
