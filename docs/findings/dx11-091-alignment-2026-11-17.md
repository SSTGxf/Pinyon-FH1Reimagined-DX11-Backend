## 4. The PRIME SUSPECT line in 0.9.1

**Prime suspect (old snapshot):** `command_processor.cpp:5172` — `const uint32_t source_row_offset = untile_band;` — where `untile_band` is computed at line 4556 from `PA_SC_WINDOW_OFFSET.window_y_offset`, which the guest resets to 0 by resolve time. It feeds the resolve compute-shader constants (line 5174), the source rect (lines 5248–5249), and the copy-down rows (lines 6430–6431). A Band-2 resolve therefore likely reads Band 0's rows instead of rows 512–719.

**In 0.9.1: cannot be verified from source — there is no source.** There is no `command_processor.cpp` in the 0.9.1 tree and no 0.9.1 line number to report.

**Binary evidence from the 0.9.1 `rexgpu-fh1.dll` (11,990,016 B):**

| `source_row_offset` | **82** |
| `untile_band` | 1 |
| `D3D11` | 1 |
| `d3d11` | 0 |
| `D3D12` | 113 |
| `Vulkan` | 632 |
| `FH1 edram3d probe` | 0 |
| `FH1 resolve probe` | 0 |

Interpretation (with the usual caveat that release-binary string counts are not a source audit):
- The resolve source-row-offset logic **is present** in 0.9.1's prebuilt binary (82 occurrences of the string, consistent with the shared command processor's resolve path and its log format strings). So the resolve path exists in 0.9.1.
- But I cannot tell from the binary whether 0.9.1's `source_row_offset` is derived from the stale `untile_band` or from the plan rect, and there is no line number to give. **The suspect is neither confirmed nor cleared in 0.9.1.**
- The probes are **not** in 0.9.1 (0 occurrences of both probe strings). They were Seth's local additions and never shipped upstream.
- `D3D11` appearing once (vs Vulkan 632 / D3D12 113) is consistent with D3D11 not being a functional backend in 0.9.1 (likely a stray mention / error string), not with a D3D11 backend being present.

**In the GitHub repo (Nov 12):** `source_row_offset` is hardcoded to 0 (per the repo's own band-mapping doc). So the repo baseline does not have the `= untile_band` line either — that line was a Nov 17 local state. When the backend is recovered from the repo, the `source_row_offset` fix (derive the band from the plan rect) should be applied directly, rather than first reproducing the `= untile_band` bug and then fixing it.

## 6. Verdict: what ports, what is missing, the plan, the blockers

### (a) What ports cleanly
- **The GitHub repo is the recoverable baseline.** Cloning `SSTGxf/Pinyon-FH1Reimagined-DX11-Backend` (HEAD bebb63e) gives the full Phase 13B D3D11 backend source: `src/graphics/command_processor.cpp`, `src/graphics/d3d11/` (executor, resolve, command processor, provider), `include/rex/graphics/d3d11/`, `src/graphics/flags.*`, and the shaders (`fh1_native_edram.hlsli`, `fh1_native_transfer.ps.hlsl`, etc.). This is the only surviving full copy of the DX11 backend.
- **The 0.9.1 kit already contains the shared resolve path** (the `source_row_offset` logic is in the prebuilt `rexgpu-fh1.dll`), so the resolve machinery the probes measure is present in 0.9.1 — only the D3D11 executor and the probes are missing.
- **The VM workspace holds the exact patch text** for the Nov 16–17 work (§7), so that work can be re-applied mechanically rather than re-derived.

### (b) What conflicts or is missing
- **The Nov 16–17 source is lost from the PC** (§2). It is not in the GitHub repo (§3.2) and not in 0.9.1 (§1). The per-band fix, edram3d probe, resolve probe, and call logger must be reconstructed.
- **0.9.1 ships no rexglue source.** The shiftglue-kit is prebuilt (headers + `.lib`s). Source patches cannot be applied to it. The D3D11 backend cannot be "dropped into" the 0.9.1 tree — there is no source tree for it to drop into.
- **0.9.1 has no D3D11 backend** (§5). This is a missing feature, not a version skew.
- **Version skew between the repo baseline and 0.9.1.** The repo is the Nov 12 Phase 13B snapshot (rexglue CMakeLists VERSION 0.10.0, detached HEAD 79d3e6fa in the old checkout); 0.9.1 is a newer upstream. The shared command processor, `Fh1PlanResolve`, flag definitions, and shader interfaces may have changed between them. A mechanical file copy of the Nov 12 D3D11 backend onto 0.9.1 is not expected to compile cleanly — it needs an integration pass against the 0.9.1 rexglue source (which is not in the 0.9.1 install).
- **The `source_row_offset` fix itself is not in any surviving source.** It was identified (Nov 17) but never patched, never pushed, and the file it lives in is gone from the PC. It must be applied fresh when the backend is recovered.

### (c) Minimal set of files / changes to bring DX11 + probes + the source_row_offset fix onto 0.9.1
1. **Recover the baseline:** clone `SSTGxf/Pinyon-FH1Reimagined-DX11-Backend` (HEAD bebb63e) to the PC. This restores `src/graphics/command_processor.cpp`, `src/graphics/d3d11/`, `src/graphics/flags.*`, and the shaders.
2. **Obtain the rexglue/ShiftGlue source for the 0.9.1 version** (upstream — separate from the launcher's prebuilt kit). Without this, there is no source tree to integrate the D3D11 backend into. This is the gating dependency; confirm where upstream publishes the 0.9.1 rexglue source before doing the rest.
3. **Integrate the D3D11 backend** from the recovered repo into the 0.9.1 rexglue source (executor, provider, resolve, flags, shaders; wire the backend selection so `--gpu_backend=d3d11` / the D3D11 adapter pick works as it did in the old snapshot).
4. **Re-apply the Nov 16–17 work from the VM's patch files** (§7), in order: (i) per-band fix, (ii) call logger, (iii) edram3d probe (EDRAM-only version), (iv) resolve probe. The probe diffs are the exact patches; re-apply them onto the recovered source and resolve any line-number drift against the 0.9.1 rexglue source.
5. **Apply the `source_row_offset` fix** (the prime suspect): in `IssueCopy`, derive the band from the plan rect (`plan.y0` / `plan.y1`) instead of the stale `untile_band` — for both the resolve probe gate and `source_row_offset`. Complete the row-math check first (whether `Fh1D3D11UntileBand` returns a band index or a row offset, and whether `plan.y0` is already 512 for Band 2 — see the open item in §6(d)); this was left unfinished when the PC went down for the reinstall.
6. **Rebuild** (with `CMAKE_BUILD_PARALLEL_LEVEL=4` to avoid clang OOM, as before), verify the DLL contains the probe strings and the fix, then run the lean D3D11 capture and read the resolve probe + staging lines during free roam.

### (d) Blockers
1. **The Nov 16–17 source is lost from the PC** (§2). Recovery depends on the GitHub repo (Nov 12 baseline) + the VM's patch files. If either is incomplete, the work must be re-derived.
2. **No rexglue source for 0.9.1 in the install.** The launcher ships a prebuilt kit only. Until the 0.9.1 rexglue source is obtained, steps 3–6 cannot proceed.
3. **0.9.1 has no D3D11 backend.** Integration is required; it is not a flag flip.
4. **Row-math check unfinished.** Whether `Fh1D3D11UntileBand` returns a band index (0/1/2) or a row offset (0/256/512), and whether `plan.y0` is already 512 for Band 2 (double-offset risk if `source_row_offset` is added on top), was not verified before the PC went down for the reinstall. Do not patch `source_row_offset` until this is checked against source.
5. **The 0.9.1 preview on C: is a stock build.** Do not confuse it with a DX11-capable build — it is Vulkan by default and contains no probes and no D3D11 backend.
